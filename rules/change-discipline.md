# 需求变更防返工纪律（AI 协作版）

> 从一次真实发布改造中总结的防返工纪律：因未提前确认接口类型、未扫描枚举全链路判断、未预设跨服务开关，导致同一需求 6 次返工 commit。
> 适用于 AI 参与的需求开发：**触发即执行，不依赖用户提醒。**

---

## 触发条件（任一满足即执行本纪律）

1. 需求涉及新增接口字段或修改字段类型
2. 需求涉及新增/扩展枚举值，且该枚举在现有代码中被 `equals` / `getCode` / `switch` 判断过
3. 需求涉及新增跨服务调用（Feign / MQ / HTTP）
4. 需求涉及新增业务开关（配置中心、灰度、特性开关）
5. 同一需求在 3 个工作日内出现 2 次以上逻辑修正 commit

---

## 阶段 1：需求冻结前必须确认

设计定稿前，用提问工具或文字一次性确认（不要挤牙膏式逐轮问）：

### 接口契约
- [ ] 每个新增字段的入参类型是否已与前端/调用方确认？
- [ ] 多选字段在接口层是 `List<T>` 还是逗号分隔字符串？
- [ ] 枚举描述字段在出参中是列表还是拼接字符串？
- [ ] 字段为空时的默认值和缺省行为是什么？

### 业务规则
- [ ] 每个新增枚举值的全部使用场景是否已列出？
- [ ] 老枚举值是否仍会被使用？旧逻辑是否需要兼容？
- [ ] 业务开关的默认值是什么？关闭时行为是什么？
- [ ] 跨服务调用失败时，阻断主流程还是仅记录日志？

### 部署与联调
- [ ] 被调用服务是否已部署？是否需要默认关闭新链路？
- [ ] 是否需要开关控制逐步上线？开关 key 是什么？哪些环境已配置？

---

## 阶段 2：设计文档强制章节

需求设计文档必须包含：

1. **接口契约表**：字段名、类型、必填、默认值、说明
2. **枚举映射表**：code、枚举名、含义、使用场景、新增/变更标记
3. **链路影响清单**：改动点、调用方、被调用方、判断该枚举/字段的位置
4. **开关设计表**：开关 key、默认值、打开行为、关闭行为、上线计划
5. **边界场景清单**：空值、老数据、灰度未命中、开关关闭、跨服务失败

验收标准必须对每个边界场景给出 Given/When/Then。

---

## 阶段 3：编码前强制影响扫描

代码改动前，必须 grep 以下内容并记录结果：

```bash
# 1. 枚举/字段是否被判断过（换成你的枚举与字段名）
grep -R "SourceEnum\.VISIT\|getSource()" --include="*.java" src/

# 2. 新增字段在 Resp/VO/DTO 中的类型是否一致
grep -R "customerType\|customerTypeDesc" --include="*.java" src/

# 3. 新增跨服务调用是否已有开关或降级
grep -R "batchSyncMembers\|MemberServiceClient" --include="*.java" src/
```

扫描后必须回答三个问题：
- [ ] 有没有遗漏的 `equals` / `switch` / 特殊分支判断？
- [ ] 新增字段是否还有另一个 DTO/VO/Resp 需要同步修改？
- [ ] 新增调用是否已有开关、超时、降级、日志？

---

## 阶段 4：提交前必须覆盖的自测场景

| 维度 | 必须覆盖 |
|------|---------|
| 业务开关 | 开 / 关 / 未配置 |
| 枚举新值 | 新值 / 旧值 / null |
| 灰度 | 命中 / 未命中 |
| 跨服务 | 成功 / 失败 / 超时 |
| 数据兼容 | 老数据 / 新数据 |

---

## 阶段 5：返工红线（触发即停）

同一需求出现以下任一情况，**暂停编码，重新回到设计确认阶段**：

1. 3 个工作日内第 3 次逻辑修正 commit
2. 新增枚举值后发现已有代码遗漏兼容
3. 跨服务调用在未通知调用方的情况下需要调整契约
4. 接口字段类型或枚举含义发生变更

---

## 与其他规则的联动

- 阶段 1-2 对应 OpenSpec SDD 的需求探询与设计文档阶段（见 [ai-dev-workflow](https://github.com/gaoqiongxie/ai-dev-workflow) 的 `openspec-propose`）
- 阶段 4 的检查项可并入提交流程的防返工门禁（`low-rework-dev-gate`）
- 阶段 5 的返工计数，对话日志和日报会自动留痕（`daily-work-review`）
