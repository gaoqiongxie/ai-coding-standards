# Git 协作安全规范（AI 协作版）

> 让 AI 在"帮你操作 Git"时不越权、不毁历史。适用于任何把 Git 操作交给 AI 编程工具的场景。

---

## 1. 分支模型（模板，按团队实际调整）

| 分支 | 用途 |
|------|------|
| `main` / `master` | 生产主分支 |
| `develop` | 开发集成分支 |
| `test` | 测试分支（SIT/UAT） |
| `feature/*` | 新功能开发 |
| `hotfix/*` | 线上紧急修复 |

---

## 2. 操作权限矩阵（AI 必须遵守）

| 操作类型 | 命令示例 | 是否需要用户确认 |
|---------|---------|----------------|
| **只读** | `git pull`（快进合并）、`git status` / `diff` / `log` / `fetch` | 直接执行 |
| **本地写** | `git add`、`git commit`、`git stash` | **需用户明确说"提交"/"commit"** |
| **远端写** | `git push`、创建 MR/PR | **需用户明确说"推送"/"push"** |
| **历史改写** | `git commit --amend`、`git rebase`、`git reset --hard`、`git push --force` | **默认禁止**（见第 3 节） |

用户说"先验证"时只验证不提交；提交信息需用户确认或按其既定格式生成后请其过目。

---

## 3. 历史红线（任何情况下不得违反）

> **AI 为什么爱犯**：AI 遇到 push 被拒时，第一反应经常是 `push -f` 或 `reset --hard`，因为"把远端改成我想要的样子"是最短路径——代价是吃掉同事的提交。

| 红线 | 原因 | 正确做法 |
|------|------|---------|
| **禁止 `git push --force` / `--force-with-lease`** | 会覆盖他人已拉取的提交 | push 被拒 → 先 `git fetch` 看远端变化 |
| **禁止 `git reset --hard` / `git rebase` 改写已推送历史** | 已推送提交是协作文物 | 用 revert 回滚；本地未推送的可用 rebase 对齐远端 |
| **未经确认禁止 `commit --amend`** | 改写已存在提交，与 force push 叠加风险大 | 要改就新提交；必须 amend 时先征得用户同意 |
| **Push 前必须先 `git fetch`** | 远端可能有新提交，避免 push 被拒返工 | 有远端新提交时：本地未推送提交 rebase 对齐，或 pull 合并后再推 |

---

## 4. 提交规范

- 提交粒度：**一个可验收点为单位**，不把无关改动混进一个提交
- 提交信息格式按团队约定（示例：`feat:<issue>#<编号> <需求名称> <具体改动>`；`fix:<issue>#<编号> <修复说明>`）
- 若项目维护任务清单（tasks.md / todo tracker）：**先更新清单勾选状态，再连同代码一次性提交**，禁止一轮需求分两次提交
- 频繁提交、及时解决冲突，不积压超大分支

---

## 5. 提交前 Checklist

- [ ] 无 `console.log` / `debugger` / `System.out.println` 残留
- [ ] 构建通过（前端 `npm run build`、后端编译通过）
- [ ] 任务清单状态已同步勾选
- [ ] 提交信息符合格式且说清"为什么"
- [ ] 无 .env、凭证、密钥、大文件混入（`.gitignore` 已覆盖）
- [ ] push 前已 fetch，无未处理的远端新提交
